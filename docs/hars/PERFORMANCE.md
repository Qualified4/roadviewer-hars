# API 예비 측정

**전체 기능 동등성 기준의 성능 비교는 아직 아니다.** Rust 목록에는 일부 파생 필드·아카이브 처리가 빠져 있고 응답 크기도 더 작다. 아래 수치를 제품 전체의 개선율로 사용하면 안 된다. 로그 변환·영상 처리·실장치 업로드·HAOS 성능은 별도 검증이 필요하다.

측정 원본은 Python `71add1a0`(1.3.16), Rust **`8b30ab7`** release 빌드다. 이후 요청 ID 전파·진행률 JSON 키·경로 사전 검증을 수정했으며, 아래 숫자는 그 이후 커밋의 재측정 결과가 아니다.

조건: WSL2 x86_64, 16 logical CPU, Python 3.12.3, Gunicorn worker 1개/threads 8개, Rust Tokio 기본 worker 수. 각각 합성 기록 200개를 준비하고 같은 로컬 파일 시스템에서 서버별 1회 측정했다. 본문 조각은 256 KiB, 8 MiB 업로드 4개를 병렬 전송했다. TLS·HA Ingress·NAS·Drive·로그/영상 변환·브라우저 렌더링은 포함하지 않는다.

RSS는 Gunicorn master/worker를 포함한 프로세스 트리 합계로, 공유 페이지가 중복 집계될 수 있다. 최고 RSS는 20 ms 간격에서 관측한 값이며 서버 전체 작업의 최대 메모리나 생산 환경 Peak RSS가 아니다. 업로드 중 UI 조회 표본은 Python 200개, Rust 537개로 다르다. CPU 총량·평균 비율 역시 동일 요청 수 비교가 아니다.

Rust는 각 조각을 디스크에 동기화한 뒤 응답하며 Python 원본은 조각별 fsync를 하지 않는다. 네트워크/Ingress/장치가 없는 loopback 시험의 실패 0건은 실환경 연결 안정성의 증명이 아니다. 짧은 1회 시험이므로 tail latency의 재현성도 확정하지 않는다.

## 변환 병목 최적화와 반복 측정 (2026-11-15)

위 3.78/4.53초는 1회 관측이다. 이번 기준은 `main 98ca299` release 실행 파일을 별도로 보존한 것이다. 환경 재부팅으로 이전 `/tmp` 결과가 없어 기준을 다시 빌드했으며 비교용 PR·CI는 만들지 않았다. 최적화 소스는 `3a645e9`다. 원본 Python과 운영 환경은 변경하지 않았다.

조건: WSL2 Ubuntu24.04 x86_64, 16 logical CPU, Rust1.100 stable, 입력은 같은 NTFS 경로, 출력은 WSL ext4. 구현별 워밍업 1회 후 순서를 회전·역순 교차한 5회씩의 중앙값이다. 전역 캐시를 비우지 않은 warm-cache 측정이며 cold-cache·HAOS 측정이 아니다. 프로파일러와 opt-in 계측은 끄고, 다른 자체 빌드·벤치와 겹치지 않게 순차 실행했다. 호스트 전체 부하·주파수는 통제하지 못했다. 각 결과의 전체 JSON 비교·썸네일 비교·입력 SHA 확인은 시간 측정 밖에서 수행했다.

### 병목의 근거와 유지한 변경

변경 전 release에 `perf cpu-clock 199Hz`를 적용한 914표본에서 손실0, `memset`19.80%(GzEncoder 호출 아래), miniz `compress_inner`13.24%, 부동소수점 포맷2.95%, malloc2.63%였다. Serde가 숫자·구두점마다 작은 write를 압축기에 전달하는 경로를 확인했다. Serde와 Gzip 사이에 64KiB 버퍼를 넣어 압축 초기화/호출 부담을 줄였다. JSON 전체를 문자열 버퍼에 올리지 않으며 level9·finish·flush·fsync를 유지한다. 이 변경만의 별도 교차5회는 기준4.69954→3.73011초, CPU4.13098→3.17080초였고 산출물 크기·JSON·Rust 썸네일은 같았다.

DHAT에서는 NAL 검사 `to_vec` 누적77.3MB, compact의 임시 flat JSON 배열28.6MB가 상위 할당이었다. NAL은 버퍼 slice를 필드별로 빌리고, compact는 동일한 finite/반올림/0.002 조건을 직접 비교한다. Cap'n Proto 리스트·telemetry 열의 불필요한 Value 복제를 소유권 이동으로 바꾸고 용량을 예약했다. 전체 동적 모델을 새 타입으로 재작성하지 않았다.

DHAT main 프로세스 누적 할당은 **970198580→671629886 bytes(30.8% 감소)**, 할당 수8480770→7424303이다. 반면 동시 live heap peak는 **232062491→232067694 bytes**로 거의 같다. 누적 할당 감소를 Peak 감소로 표현하지 않는다. 프로세스 트리 RSS와 DHAT live heap도 다른 지표다. 큰 모델/replay Value 트리는 여전히 주요 상주 비용이다. DHAT가 집계한 memory writes는113521411945→1419039985 bytes였으며, 이는 메모리 접근량이지 디스크 쓰기량이 아니다.

### 영상 작업량과 단계별 진단

기존 MP4의 Python 경로는 qcamera PTS 수집과 검증을 별도로 읽고, 전방·와이드는 PyAV 안에서 패킷 검사·SHA를 함께 처리한다. 썸네일만 제한된 픽셀 디코딩을 한다. Rust는 ffprobe로 패킷 시각을 확인하고 별도 FFmpeg 스트림으로 NAL SHA/헤더를 검증한다. 같은 작업에서도 프로세스 시작·동적 라이브러리 초기화·JSON IPC·파일 재읽기 비용이 추가된다. 단순히 같은 FFmpeg를 쓴다고 동일한 작업량이 아니다.

동일 변환 작업 안에서 ffprobe의 stream/packet 결과를 재사용해 3카메라 재사용 경로의 probe를8→4회, 총 native 프로세스를12→8개로 줄였다(4 probe+3 bitstream 검사+1 thumbnail). 작업 간 캐시는 두지 않는다. 코덱·단일 영상 stream·크기·짝수 해상도·프레임 수·PTS/DTS·decoder header·SHA 검증을 유지하고 raw 입력의 B-frame 검사와 출력 검증도 유지한다. 영상 검사를 replay geometry 할당 전에 수행해 자식 RSS와 큰 frame 트리가 겹치는 시간을 줄인다.

### 품질 차이·남은 비용

HEVC에서 기존 FFmpeg6 출력은 샘플 안의 VPS/SPS/PPS와 hvcC를 함께 남겨 정규화 Annex B 확장 시 각60→120개로 중복했다. VCL2400개(2 slices/frame)는 변하지 않았다. Python/FFmpeg8은 샘플에서 이를 제거한다. [FFmpeg6 muxer](https://github.com/FFmpeg/FFmpeg/blob/n6.1/libavformat/movenc.c)와 [FFmpeg8 muxer](https://github.com/FFmpeg/FFmpeg/blob/n8.0/libavformat/movenc.c)의 parameter-set filtering 차이도 확인했다. 원본 해시 계산 후 `filter_units`로32/33/34만 제거하고 hvcC에 보존해 새 hvc1 출력을 맞췄다. 재인코딩·VCL/SEI 변경은 하지 않는다. 최종26영상 모두 정규화 **전체 NAL** SHA가 입력과 일치하고 디코딩1200프레임/오류0이다. 기존 MP4를 강제로 다시 쓰지는 않는다.

**정정(2026-11-16): 이 차이는 해소됐고 아래 원인 설명은 틀렸다. 실제 원인은 `ffmpeg`/`ffprobe` CLI가 강제하는 `scan_all_pmts=1`이며, qcamera 리먹싱을 libavformat 기본값 경로로 바꾼 뒤 13/13 동등이다. 아래 "영상 리먹싱 3자 비교" 절을 따른다.** 당시 기록: 13구간 중3/9번의 TS 마지막 sample duration은 Python4481/4518ticks, Rust4500ticks(90kHz)로 다르다. 입력 탐색 경로의 inferred rate는 Python241/12·239/12, Rust20이었다. 약+0.211/-0.200ms의 파생 길이 차이가 replay/telemetry/summary duration에 전달된다. 부동소수 오차로 숨기지 않았고 `1e-6`을 넓히지 않았다. 이는 baseline부터 있던 **미해결 메타데이터 호환 차이**이며 새 최적화 회귀가 아니다. FFmpeg/PyAV 버전과 탐색 설정 각각의 기여는 분리하지 못했다. 해당2구간도 압축 NAL·PTS/DTS·프레임·시킹 검사는 통과했지만 전체 JSON의 Python 동등성은 **11/13**이다. 최적화 전후 Rust는13/13 동일하며 기존61구간은 최종 코드로 차이0이다.

## 영상 리먹싱 3자 비교: Python · Rust(FFmpeg 엔진) · Rust(순수 엔진) (2026-11-16)

기준 소스 `d849d10`. 같은 실행에서 세 구현을 교차 측정했다. **Rust(순수 엔진)은 FFmpeg 없이 리먹싱하는 실험 구현**(`--features pure-remux`, 기본 꺼짐)이며 제품 변환 경로에 연결되어 있지 않다. 따라서 이 표는 **영상 리먹싱 단계만**의 비교다. 로그 변환·썸네일·업로드를 포함한 전체 변환 시간의 비교가 아니다.

조건: WSL2 Ubuntu 24.04 x86_64, 16 logical CPU, Rust 1.100 release, 시스템 FFmpeg 6.1.1, PyAV 16.1.0. 입력은 원본 형식 13구간의 영상 26개(NTFS drvfs, 읽기 전용), 출력은 ext4. 구현별 warmup 1회 뒤 순서를 회전·역순 교차해 영상마다 5회, 표본은 26영상 × 3구현 × 5회 = 390개다. 세 구현 모두 검증 포함 작업(입력 압축 그림 해시, 리먹싱, 출력 검사)이다. 모든 출력은 측정 구간 밖에서 Python 출력과 PTS/DTS(1e-6초), 키프레임 인덱스, 압축 그림·decoder header 서명을 대조했고 390개 전부 통과했다. 도구는 `integration/benchmark_remux.py`이며 순수 엔진은 `remux`를 `__pure-remux`로 바꿔 부르는 한 줄 sh wrapper를 거친다(wrapper의 exec 비용이 순수 엔진 쪽에 포함된다).

### 읽는 법

- **순수 엔진이 두 형식 모두에서 가장 빠르다.** 회차 범위가 다른 두 구현과 겹치지 않는다. HEVC는 Python의 0.47배, TS는 0.28배 시간이다. CPU는 각각 0.34배, 0.29배, 최고 RSS는 약 33 MiB로 Python(약 50 MiB)과 FFmpeg 엔진(69~93 MiB)보다 낮다.
- **현재 제품 경로(FFmpeg 엔진)는 HEVC에서 Python보다 16% 느리다.** 회차 범위가 겹치지 않는다. TS는 범위가 겹쳐 측정 가능한 차이가 없다.
- **무엇이 수치를 제한하는가.** FFmpeg 엔진의 추가 시간은 별도 worker 프로세스 기동, FFmpeg 초기화, 출력 재검사에서 나온다(앞 절의 perf·strace 기록). 순수 엔진의 HEVC 시간은 대부분 NTFS 입력 읽기와 SHA-256이다. 같은 날 별도 진단에서 대표 파일(37.5 MB)을 drvfs에서 읽기만 하는 데 약 0.16초가 걸렸고 ext4 입력에서는 순수 엔진 코어가 0.07초였다([진단 수치](measurements/pure-remux-2026-11-16.json)). 13영상이면 읽기만 약 2초이므로 순수 엔진의 3.5초 중 절반 이상이 입력 I/O라는 계산이다(추정). 137.8 MB/s는 디스크·해시 한계 안의 값이다.
- **전체 변환에서의 비중(추정).** 구간 하나의 전체 변환은 이전 측정에서 약 3.2초였다(1번 구간, 앞 절). 이번 표에서 FFmpeg 엔진의 구간당 리먹싱은 (8.804+2.221)/13 = 0.85초, 순수 엔진은 (3.547+0.597)/13 = 0.32초다. 순수 엔진으로 바꾸면 구간당 약 0.53초, 전체 변환의 약 16%가 줄어든다는 계산이 되지만, 서로 다른 날의 측정을 합친 추정이며 순수 엔진을 제품 경로에 연결해 직접 잰 값이 아니다.

| 파라미터 세트만 100 MB | 2,056 MiB에서 상한에 걸려 실패 | 34.7 MiB, `invalid`로 거부 |
| SEI만 100 MB | 2,056 MiB에서 상한에 걸려 실패 | 34.2 MiB, `invalid`로 거부 |
| 33 MiB NAL 하나 | 157.6 MiB | 95.4 MiB, `invalid`로 거부 |

압축 sample을 메모리에 두던 구조를, 이름 없는 임시 파일에 쓰고 정확한 크기의 `ftyp+moov` 뒤로 `copy_file_range`로 옮기는 구조로 바꿨다. 메모리는 입력 바이트가 아니라 프레임 수를 따른다(프레임당 약 1.6 KB, 입력 MB당 기울기 0.05 MiB). 빈 worker가 약 33 MiB다. worker에는 실측 크기 + 256 MiB의 `RLIMIT_AS`가 걸린다. 26영상의 출력은 변경 전과 바이트 단위로 같다. 입력을 두 번 읽는 대안은 같은 36 MiB였지만 drvfs에서 0.503초로, 채택한 방식의 0.305초보다 느렸다(대표 영상 1회).

### 내구성과 여유 공간 검사의 비용 (교차 5회)

| 측정 | 추가 전 `3834c10` | MP4 fsync 추가 | 최종(fsync + 쓰기 먼저 시작) |
|---|---:|---:|---:|
| HEVC 13영상 리먹싱(초), 2차 실행 | 5.007 | 5.444 | 5.253 |
| 전체 변환 3구간(초) | 9.667 | 9.848 | 측정 안 함 |

게시 rename 전에 MP4와 폴더를 fsync한다. 원본 비보존 설정에서 원본 삭제는 그 뒤에만 일어난다. 비용은 HEVC 리먹싱에서 4.9%(영상당 약 19 ms), 전체 변환에서 1.9%(회차 범위 안)다. 순수 엔진 시작 전에 여유 공간이 입력의 2배 + 100 MiB 미만이면 한 벌만 쓰는 FFmpeg 엔진을 고른다. 이 판정의 비용은 측정에서 구분되지 않았다.

### 무엇이 수치를 제한하는가

- 순수 HEVC 리먹싱: drvfs 입력 읽기와 SHA-256 두 번(입력 서명, 출력 판독), 그리고 MP4 fsync.
- 순수 TS 리먹싱: 입력이 약 2.3 MB라 프로세스 기동과 FFmpeg 입력 검사 worker가 대부분이다.
- 전체 변환: 로그 해석(zstd), 텔레메트리, 로그 분석의 CPU. 리먹싱은 약 10분의 1이다.
- 동시 변환: 변환당 CPU와 로그 분석 메모리.

미측정: HAOS·aarch64, cold cache, 최종 커밋(쓰기 먼저 시작)에서의 전체 변환, 리먹싱 단독과 전체 변환의 구현별 최고 RSS 집계.

WSL2 Ubuntu 24.04, 같은 기계. 측정 원본은 `measurements/ffmpeg-image-amd64-2026-11-17.json`, `no-ffmpeg-*.json`, `pure-reverse-2026-11-17.json`, `thumbnail-decoder-2026-11-17.json`이다.

- aarch64 크기는 CI의 `Container (aarch64)` 작업 요약과 artifact에 남는다.
